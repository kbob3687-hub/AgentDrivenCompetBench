# 剩余6天 P0/P1/P2 待办

> 目标：提交前把项目从“功能很多但演示不稳”收口到“可稳定答辩、可解释失败、可证明闭环”的状态。

## 当前最关键结论

Feishu + SaaS 三轮空不是 Discovery 问题。Discovery 已经通过 warm path 找到 `feishu.cn` 的 5 个 URL，真正失败点在 Collector：Firecrawl 额度不足，HTTP 抓到 JS 空壳，Playwright 本地兜底报 `NotImplementedError`，最终 0 claims，后续 Analyst/Writer 没东西可做。

Firecrawl 不是不好，而是当前项目把它用得太粗：默认调用、每个 URL 重试、多轮重复撞失败 URL、open_search 搜索时还可能顺手 scrape 正文，所以 credits 消耗快，但失败时没有收益。

## Playwright 是什么

Playwright 是一个浏览器自动化工具。它可以在后台启动 Chromium，像真实用户一样打开网页、等待 JavaScript 渲染完成，再读取页面文本。

在本项目里，它的定位应该是“免费本地兜底”：当 `direct_http` 只能抓到 JS 空壳时，用 Playwright 渲染页面。Feishu、Notion、很多 SaaS 官网都属于这种现代前端页面。

Playwright 本身不是大问题，它是成熟工具。当前问题是项目集成和本机运行环境没兜住：

- Windows 下如果事件循环策略不对，Playwright 启动浏览器子进程可能报 `NotImplementedError`。
- 如果没安装 Chromium 浏览器，也会失败。
- 它比 HTTP 慢，需要超时、并发限制和清晰日志。

结论：Playwright 是 P0。不是因为它危险，而是因为“不用付费抓取时，它是 SPA 页面能不能跑出来的关键兜底”。

## P0：不做会影响现场演示

### 1. 付费抓取默认关闭

问题：现在 Firecrawl/Jina 容易在日常测试中被默认消耗。Feishu 5 个 URL 加重试就可能烧很多 credits。

要做：

- 加 `ENABLE_FIRECRAWL=false`，默认不开。
- 加 `ENABLE_JINA=false`，默认不开。
- 加 `FIRECRAWL_MAX_CALLS_PER_RUN=3`。
- 加 `JINA_MAX_CALLS_PER_RUN=3`。
- 前端/日志显示当前 fetch mode，避免不知道是否在烧钱。

验收：

- 不配 key、不打开开关时，运行任务不会调用 Firecrawl/Jina。
- 打开开关后，每个任务最多调用配置次数。
- 出现 `PaymentRequiredError` 后，本任务立刻熔断 Firecrawl。

### 2. 免费抓取链路可用

问题：不用 Firecrawl 时，Feishu 这类 SPA 页面现在会变成 `HTTP 内容过短 + Playwright NotImplementedError`。

要做：

- 抓取顺序改为免费优先：`robots -> direct_http -> playwright`。
- 只有显式开启时才进入 `jina/firecrawl`。
- 修 Windows 下 Playwright 事件循环问题。
- 补充启动前检查：浏览器没安装时提示 `uv run playwright install chromium`。

验收：

- Playwright 不再报空白 `NotImplementedError`。
- 即使抓不到，也能显示明确错误：事件循环、浏览器未安装、超时、被站点拦截。

### 3. no profile 诊断说真话

问题：Feishu 明明是“找到 URL 但抓取失败”，前端却提示“Discovery 未发现 URL / Jina 配额”，误导用户继续点 continue。

要做：

- 按失败类型展示不同原因：
  - `collector_no_sources`：没找到 URL。
  - `collector_fetch_failed`：URL 找到了，但抓取/抽取失败。
  - `collector_no_claims`：抓到了内容，但 LLM 没抽出 claims。
  - `analyst_empty_profile`：有 claims，但 Analyst 没生成 profile。
- 展示前 3 条失败 URL 和主要错误。

验收：

- Feishu 失败时显示：URL 已发现，但抓取全失败。
- 日志能看到 Firecrawl 额度、HTTP 空壳、Playwright 不可用分别是什么。

### 4. 继续迭代不能原地打转

问题：人工补的 `https://feishu.com` 失败后，下一轮没补新 URL，系统仍然复用旧失败 URL。

要做：

- `continue` 且没有新 URL 时，清空上一轮失败的 `target_urls`。
- 重新走系统发现或策略降级。
- 同一任务内记录失败 URL，下一轮默认排除。

验收：

- 第二轮手动 URL 失败后，第三轮不再自动复用它。
- 除非用户重新填这个 URL。

### 5. 策略降级真实触发

问题：官方 URL 都抓不下来时，继续撞官方 URL 没意义。

要做：

- `collector_fetch_failed` 且当前是 `official_only` 时，下一轮建议 `open_search`。
- 前端 HITL 面板显示“建议从 official_only 切到 open_search”。
- open_search 先只找 URL，不默认 scrape 正文。

验收：

- Feishu 第一轮官方抓取失败后，第二轮能换数据源策略，而不是重复抓同一批失败页面。

### 6. SSE 日志去重

问题：前端开头看到 Discovery/Collector 重复，是 SSE history 回放和 queue 消费重复。

要做：

- 后端 subscribe 回放 history 后，不再重复消费 queue 中同一批事件。

验收：

- 新任务开头不会重复出现两遍 `已加载行业模板`、`Discovery started`、`Fan-out`。

### 7. 黄金演示链路

要固定 3 条演示路径：

- `Notion + SaaS`
- `Feishu + SaaS`
- `Insta360 + hardware`

每条都要验证：

- 能发现 URL。
- 能采到 claims，或失败原因清楚。
- 能生成 profile。
- 能生成 report。
- 来源链接能点。
- QA 打回和人工介入能解释。

## P1：做了明显加分

### 1. Discovery 降低 Firecrawl 消耗

问题：open_search 用 Firecrawl Search 时带 `scrape_options`，会把搜索变成“搜索 + 抓正文”，很贵。

要做：

- 搜索阶段只拿 URL/title/description。
- 选出高价值 URL 后，再按预算抓正文。

验收：

- open_search 不会因为 9 条 query 烧掉大量 scrape credits。

### 2. URL 质量排序

要做：

- 官方 pricing/product/docs 优先。
- 官方 support/manual 其次。
- 可信媒体/开发者文档再次。
- 普通博客/论坛最后。

验收：

- Fan-out 不再一股脑抓 10 个 URL。
- 每轮抓取 URL 数可控，且排序可解释。

### 3. 抓取缓存

要做：

- 同一任务内同一 URL 不重复抓。
- 同一轮失败 URL 记录失败原因。
- 多轮 QA 不重复烧同一 URL 的额度。

验收：

- 同一 URL 三轮最多抓一次，除非用户强制重试。

### 4. 溯源可信度收口

问题：最终报告不能出现空 URL 或占位 source。

要做：

- `_placeholder_source()` 只能用于内部构建，不能进入最终报告。
- Writer 输出前过滤无 URL 来源。
- QA 对空 URL source 判 major/critical。

验收：

- 报告附录里的每个来源都有可点击 URL。

### 5. QA 闭环展示

要做：

- 显示每轮缺失字段。
- 显示打回给哪个 agent。
- 显示下一轮新增 claims 数。
- 显示 resolved/regressed 字段。

验收：

- 答辩时能清楚解释“不是假闭环，重做后质量确实变好”。

### 6. 指标真实化

问题：指标页不能硬写 traceability=1.0 这类漂亮数字。

要做：

- 来源覆盖率按真实 EvidencedClaim 计算。
- 采集源数量按真实成功 URL 计算。
- 人工介入率按 HITL 次数计算。

验收：

- 指标能经得起评委追问。

## 当前判断

这套系统的核心不是“必须有 Firecrawl 才能跑”，而是要有两种模式：

- 开发测试模式：默认不烧钱，失败也能解释清楚。
- 最终演示模式：开启受控的 Firecrawl/Jina 预算，提高成功率。

只要 P0 做完，项目才有稳定答辩的基础。P1 做完，才有机会把“多 Agent 协作”和“可信输出”讲成优势。
