# AgentDrivenCompetBench 完整评测开发文档

> 目标：用 3–5 天、¥30–50 的预算，补齐一套能支撑简历数字的 Benchmark。
> 核心原则：先固定实验口径，再写代码和跑实验；所有数字必须能回到原始输出、网页快照、配置和人工裁决记录。

## 1. 已确认约束

| 项目 | 约束 |
|---|---|
| 开发周期 | 3–5 天 |
| API 预算 | ¥30–50，正式运行前必须通过冒烟实验估算总成本 |
| 人工工作量 | 50–100 次判断；采用原文对照、草稿标签、用户确认的方式 |
| 首要目标 | 同时证明内容质量、返工工程价值和质量成本 |
| 数据来源 | 正式对照使用固定网页快照；另跑少量实时网页冒烟测试 |
| 统计边界 | 小样本，不写“统计显著”；重复运行不冒充独立产品样本 |

## 2. Benchmark 最终要回答的问题

1. **系统能不能稳定完成任务？**
   - 工作流成功率、Schema 合规率、维度覆盖率、引用覆盖率是多少？
2. **多 Agent 是否比单次 LLM 更有价值？**
   - 在完全相同的网页证据下，内容可靠性和结构质量是否更好？
   - 为此多付出了多少时延和 Token？
3. **QA 与返工是否值得保留？**
   - 无 QA 与修复后 QA 的差异是什么？
   - QA 提出的返工有多少真正执行，有多少字段问题被解决？
4. **这次返工代码修复是否有效？**
   - 旧返工与新返工在相同 case、相同快照下有什么差异？
5. **证据不足和真实网站故障时是否可靠？**
   - 会不会编造？是否如实披露未知？
   - 实时抓取是否仍能工作？

## 3. 不做什么

本期不开发以下能力：

- 不做新的 Benchmark 可视化平台或前端页面。
- 不把 LLM Judge 分数当作事实准确率。
- 不为了扩大样本量而无意义地增加 repeat。
- 不为了得到正向结论而删除失败任务、降低阈值或更换统计口径。
- 不在生产代码中长期保留 `legacy_rework` 开关；旧版对照通过固定代码构建实现。
- 不声称一次实验同时证明了实时采集能力和快照回放下的内容质量。

## 5. 总体实验设计

### 5.1 Case 集

正式集包含 **6 个产品、12 个 case**：

- 每个产品 1 个常规 case：官网定价、功能、用户画像等证据较完整。
- 每个产品 1 个压力 case：缺少关键来源、证据较浅或存在来源冲突。
- 每个 case 固定 2 个待核验 Gold Slot，共 24 个。
- 6 个产品是独立产品样本；12 个 case 是任务样本；repeat 只用于观察稳定性。

Case 选择原则：

- 优先复用现有 Notion、ClickUp、OpenProject 等已经采集过的材料。
- 新增产品必须能在预算内获得可读网页快照。
- 压力 case 通过减少输入来源或选择真实冲突来源构造，不篡改网页正文。
- 正式运行前冻结 case 列表，不能根据实验结果替换“不好看”的 case。

建议数据表：

| 字段 | 含义 |
|---|---|
| `case_id` | 稳定任务 ID |
| `product` | 产品名称 |
| `case_type` | `normal` / `stress` |
| `snapshot_id` | 固定快照包 ID |
| `expected_dimensions` | 期望分析维度 |
| `gold_slots` | 2 个待人工核验的事实或未知槽位 |
| `difficulty_reason` | 压力 case 的构造原因 |

### 5.2 核心实验臂

| 实验臂 | 输入 | 工作流 | 主要回答的问题 |
|---|---|---|---|
| `single_llm` | 相同快照正文 | 一次 LLM 调用直接生成 profile 与报告 | 多 Agent 是否优于简单基线 |
| `multi_agent_no_qa` | 相同快照，经回放 Collector | Discovery/Collector/Analyst/Writer，无 QA | 多 Agent 基础能力 |
| `multi_agent_qa_fixed` | 与上面完全相同 | 完整工作流与修复后 QA 返工 | QA 的质量贡献与成本 |

补充实验臂：

| 实验臂 | 范围 | 目的 |
|---|---|---|
| `multi_agent_qa_legacy` | 6 个压力 case | 与新返工直接比较，验证代码修复效果 |

单次 LLM 基线必须满足：

- 使用与多 Agent 相同的模型、快照正文、任务维度、输出 Schema 和 Token 上限口径。
- 只调用一次 LLM，输出包含 `profile` 与 `report_markdown` 的 JSON。
- 不调用 Collector、Analyst、Writer、QA 等中间 Agent。
- 解析失败、输出缺字段或超时均按失败记录，不能人工补救后仍算原结果。
- 因输入正文需要压缩时，所有实验臂使用同一压缩规则和相同正文版本。

### 5.3 运行矩阵与预算

#### 主实验

- 12 case × 2 repeat × 3 核心实验臂 = **72 次任务执行**。
- 每个两两对比有 12 × 2 = **24 个配对位置**。
- 内容人工核验只使用预先指定的 `repeat=1`，其余 repeat 用于自动指标与稳定性分析。

#### 返工修复对照

- 6 个压力 case × 2 repeat × 2 代码版本 = **24 次任务执行**。
- 旧版与新版必须使用相同 Benchmark harness、case、快照和模型配置。
- 代码差异只能是返工修复相关补丁，不能同时混入其他生产代码变化。

#### 实时网页冒烟

- 6 个常规 case × 1 次 × 修复后完整工作流 = **6 次任务执行**。
- 实时结果单独报告，不与快照结果混合计算内容提升。

总上限为 **102 次任务执行**。这只是上限，不代表必须一次性全部运行。

### 5.4 成本闸门

正式运行前：

1. 选 3 个 case，分别运行 3 个核心实验臂，共 9 次任务。
2. 根据真实 Token/账单估算 72 次主实验、24 次返工对照和 6 次实时冒烟成本。
3. 至少保留 ¥5 预算用于失败重跑和实时冒烟。
4. 若预计超过预算，在正式运行前缩小范围，并同步修改文档和 manifest。

缩小范围的优先顺序：

1. 减少旧/新返工对照的 case 数。
2. 减少主实验 repeat，从 2 降为 1。
3. 最后才减少产品数。

不得在实验中途只给某一实验臂减少 repeat 或更换模型。

## 6. 开发一：固定快照与工作流回放

### 6.1 目标

让不同实验臂、不同代码版本读取完全相同的网页正文，消除实时网页变化和抓取故障对内容对照的干扰。

### 6.2 快照包格式

建议新增 `benchmark/snapshots/<snapshot_id>/`：

```text
manifest.json
sources/
  <url-hash>.json
```

`manifest.json` 至少记录：

- `snapshot_id`、创建时间、case_id、产品名。
- 每个 URL 的抓取时间、最终 URL、HTTP/抓取状态。
- 正文 SHA-256、标题、正文长度、抓取器版本。
- 采集时代码 commit 和必要的采集配置。

每个 source 文件至少包含：

- 原始 URL、最终 URL、标题、正文。
- 抓取状态和错误信息。
- 正文哈希及可选的响应元数据。

### 6.3 回放要求

- `replay` 模式禁止悄悄退回实时抓取。
- URL 缺失、正文哈希不一致、快照版本不兼容时直接失败。
- 多 Agent 臂在 Collector 抓取边界读取快照，后续 LLM 抽取和分析仍正常运行。
- 单次 LLM 臂读取同一份快照正文。
- manifest 记录 `source_mode=replay` 和 `snapshot_id`。
- compare 默认要求配对任务使用相同 `snapshot_id`。

### 6.4 建议修改点

- 新增 `benchmark/replay.py`：快照读取、校验和正文加载。
- 修改 `benchmark/workflow.py`：支持 `source_mode=live/replay`。
- 修改 `benchmark/models.py`：增加快照与实验臂配置。
- 修改 `benchmark/runner.py`：增加 CLI 参数并把配置写入 manifest。
- 在 Collector 抓取边界提供可注入的 fetcher；默认仍为现有实时抓取，不影响生产默认行为。

### 6.5 验收测试

- 回放时禁用网络仍能完成工作流。
- 缺 URL、坏哈希和缺快照文件会明确失败。
- 两个实验臂读取到的正文哈希完全一致。
- 实时模式行为不变。
- compare 遇到不同快照会阻止直接比较。

## 7. 开发二：单次 LLM 基线

建议新增 `benchmark/baselines/single_llm.py`，复用现有任务记录和指标，不另建一套结果格式。

输出处理流程：

1. 加载固定快照和 case。
2. 按统一规则打包正文。
3. 一次 LLM 调用生成 `profile + report_markdown`。
4. 使用现有容错解析和 Pydantic 校验。
5. 保存原始输出、Token、时延、错误和执行元数据。
6. 调用同一套 `evaluate()` 计算可适用的指标。

指标适用性：

- workflow_success 仍按“任务完成、无错误、profile/report 非空”计算。
- QA pass、返工执行率等对该实验臂为 `N/A`，不能记 0 后参与 QA 指标平均。
- Collector 抓取成功率对该实验臂为 `N/A`。
- Token 和时延必须记录，不能因流程短就缺省。

## 8. 开发三：旧/新返工代码对照

当前 `benchmark/compare.py` 要求 Git commit 相同，这是普通 A/B 的正确防呆，不能直接删除。

新增专用比较模式：

- `comparison_type=config_ablation`：默认，要求代码版本相同。
- `comparison_type=code_ablation`：允许代码版本不同，但必须显式指定。

`code_ablation` 必须额外记录和校验：

- 旧版、新版完整 commit 或构建 ID。
- 相同 Benchmark harness 版本。
- 相同 case、快照、模型、repeat、并发和 Token 配置。
- 代码差异范围说明。
- 报告中永久显示两个代码版本，不能只写“A/B”。

返工修复基线以提交 `8b699b6` 的父版本为旧返工实现、该提交为新返工实现；正式实验时还应冻结包含新 Benchmark harness 的实验构建，避免把 harness 变化误算成返工效果。

## 9. 开发四：内容可靠性人工评测

### 9.1 为什么必须人工参与

现有自动指标能判断“有没有引用”“URL 是否有效”“Schema 是否完整”，但不能证明报告结论真的被原文支持。简历中的“有依据结论率”“无依据结论率”必须来自快照原文与报告内容的人工裁决。

### 9.2 抽样方案

- 12 个 case，每个预先指定 2 个 Gold Slot，共 24 个。
- 3 个核心实验臂分别核验，共 24 × 3 = 72 次输出判断。
- 24 个 Gold Slot 的候选事实本身需要 24 次原文确认。
- 总人工工作量约 **96 次判断**；若时间不足，降为 18 个 Slot，共 72 次判断。
- 已签核且与同一快照、同一 Slot 完全兼容的材料可以减少重复工作；报告输出标签不跨 run 或实验臂复用。

### 9.3 人工裁决流程

1. 助手根据快照生成 Gold Slot 草稿和原文对照。
2. 用户确认候选事实是否准确、是否应判为未知。
3. 冻结 Gold Slot，再运行正式实验。
4. 将三个实验臂输出随机命名为匿名版本，避免知道架构后产生偏向。
5. 每条向用户展示：大白话结论、报告原文、快照原文、建议标签。
6. 用户确认或否定建议标签；助手负责修改并记录理由。
7. 每批结束报告已完成数和剩余数。
8. 使用现有签核器记录签核人、时间、时区、逐项标签和内容哈希。

### 9.4 标签定义

| 标签 | 含义 |
|---|---|
| `supported` | 报告结论被快照原文完整、直接支持 |
| `partial` | 有部分依据，但存在夸大、遗漏关键限制或表述不完整 |
| `unsupported` | 没有依据或与原文矛盾 |
| `honest_unknown` | 证据不足时明确写未知/未披露，没有编造 |
| `missing` | 应覆盖的适用 Gold Slot 没有出现在输出中 |

同一标签必须只依据本次输出和本次快照，不因为“上一轮是对的”就复用。

### 9.5 内容指标公式

设适用 Gold Slot 数为 `G`：

- **Gold 覆盖率** = `(supported + partial) / G`
- **完整支持率** = `supported / (supported + partial + unsupported)`
- **无依据结论率** = `unsupported / (supported + partial + unsupported)`
- **部分支持率** = `partial / (supported + partial + unsupported)`
- **诚实未知率** = `honest_unknown / 应当披露未知的 Slot 数`
- **遗漏率** = `missing / G`

报告必须同时给分子和分母。`partial` 不悄悄计入完整支持率，也不直接等同于完全错误。

内容指标只代表本次 24 个 Slot 的人工核验结果，不宣称代表整个互联网或所有产品。

## 10. 指标体系与简历数字来源

### 10.1 自动指标：全部正式任务

| 指标 | 口径 | 可用于简历的条件 |
|---|---|---|
| 工作流成功率 | 成功任务 / 全部任务，失败和缺失计 0 | 所有实验臂同一公式 |
| Schema 合规率 | 符合 Schema 的任务 / 全部任务 | 解析失败不得剔除 |
| 维度覆盖率 | 实际覆盖维度 / 期望维度 | 快照证据不足需同时报告压力 case |
| 引用覆盖率 | 有符合形式引用的结论 / 应引用结论 | 不能解释为事实准确率 |
| 实际返工执行率 | 至少执行一次真实返工的 revise 任务 / revise 任务 | Discovery 空跑不算实际返工 |
| 字段问题解决率 | `resolved_fields / (resolved_fields + persisted_fields)` | 同时报告新增回归字段 |
| 来源受限终止率 | `source_limited` 任务 / revise 任务 | 不能一律算作系统失败或成功 |
| 时延 | 任务端到端秒数，报告均值和中位数 | 同一 timeout 与并发配置 |
| Token | 仅使用 usage 完整的任务 | 不完整时标 unknown，不能记 0 |
| 成本 | 实际账单或明确价格模型估算 | 记录价格来源与日期 |

### 10.2 三个关键差值

1. **多 Agent 架构价值** = `multi_agent_no_qa - single_llm`
2. **QA 质量与成本** = `multi_agent_qa_fixed - multi_agent_no_qa`
3. **返工修复效果** = `multi_agent_qa_fixed - multi_agent_qa_legacy`

每个差值都要同时查看质量、时延和 Token，不能只挑选有利的一项。

### 10.3 主统计口径

- 全任务质量结论使用 `all_tasks_summary`，失败和缺失质量值计 0。
- 仅成功任务的结果可作为次要分析，不能替代主结果。
- 按 `(case_id, repeat, snapshot_id)` 配对。
- 同一产品 repeat 不是新的独立产品样本。
- 报告样本数、缺失配对数和失败原因。
- 不写“统计显著”；可以写“本实验提升/下降了 X 个百分点”。

## 11. 开发五：多实验总报告

建议新增 `benchmark/summary.py`，输入多个 run，输出一个总目录：

```text
benchmark_summary.md
summary.json
runs/
content_review/
```

总报告固定包含：

1. 实验目的与冻结日期。
2. 产品、case、repeat、实验臂和代码版本矩阵。
3. 模型、Token 上限、并发、快照 ID 和配置哈希。
4. 全任务主结果表。
5. 三个关键配对差值。
6. 内容人工核验结果及分子/分母。
7. 实际返工、字段解决、回归字段和来源受限分析。
8. 时延、Token 和成本。
9. 实时网页冒烟结果，单独成节。
10. 失败案例和局限。
11. 每个数字对应的 raw/metrics/review 文件链接。

报告中自动加入防误读说明：

- 引用覆盖率不是事实支持率。
- 人工内容指标只覆盖指定 Slot。
- 实时冒烟不与回放主实验混合。
- 旧/新代码对照与普通配置 A/B 分开显示。

## 12. 实时网页与故障稳健性

实时冒烟只回答：

- 当前真实网站是否还能抓取和分析。
- 抓取成功率、任务成功率、时延和错误类型如何。
- 无来源、抓取失败、JSON 解析失败时系统是否按预期终止或披露。

至少保留以下测试：

1. 正常实时来源。
2. 固定 URL 无新来源可补。
3. 网页抓取失败。
4. 模型输出 malformed JSON。
5. 证据不足时应披露未知。
6. 来源之间存在冲突。

实时网页失败不能直接算作快照内容实验中的系统质量下降；两种结果分别报告。

## 13. 测试与验收标准

### 13.1 代码验收

- 快照回放禁用网络可运行，缺失或篡改快照会失败。
- 单次 LLM 基线确认只发生一次 LLM 调用。
- 三个实验臂复用同一指标入口和结果 Schema。
- compare 能阻止不同快照、模型、repeat、并发配置被误配。
- code_ablation 能显示并核对两个代码版本。
- 失败、超时、空输出和 Token 缺失均按既定口径落盘。
- 总报告中的每个数字都可追溯到原始文件。
- 现有测试和新增 Benchmark 测试通过；无关既有失败需单独记录。

### 13.2 实验验收

- 正式 case、快照、Gold Slot 和实验矩阵在运行前冻结。
- 主实验 72 次任务均有结果或明确失败记录。
- 每个核心对比有完整配对清单和缺失配对说明。
- 24 个 Gold Slot 与 72 个输出判断完成签核，或按预先缩小的 18 Slot 方案完成。
- 旧/新返工对照只包含允许的代码差异。
- 实时冒烟单独报告。
- 没有出现为了获得正向结论而删除失败、改阈值或复用旧标签的情况。

## 14. 3–5 天实施顺序

### 第 1 天：冻结设计与快照回放

- 确定 6 个产品、12 个 case 和 24 个 Gold Slot 草稿。
- 实现快照包、回放和配置防呆。
- 完成回放单元测试。
- 保存正式快照并冻结哈希。

### 第 2 天：基线与冒烟成本估算

- 实现单次 LLM 基线。
- 接入三个核心实验臂。
- 运行 9 次冒烟任务，检查输出和 Token。
- 估算总成本，冻结最终 repeat 和实验范围。

### 第 3 天：正式主实验与 Gold 确认

- 串行启动主实验，持续汇报进度和失败情况。
- 用户确认 24 个 Gold Slot。
- 主实验完成后先检查配置和缺失配对，不先看“哪组更好看”。

### 第 4 天：内容裁决与返工对照

- 完成 72 次匿名输出裁决。
- 运行旧/新返工对照。
- 实现并生成多实验总报告。

### 第 5 天：实时冒烟与简历数字提取

- 运行 6 次实时冒烟。
- 复核所有公式、分母、失败样本和成本。
- 从总报告提取简历数字。
- 保存一份可复现命令与结果索引。

若只有 3 天，优先保证主实验、内容裁决和返工对照；实时冒烟与总报告美化可以压缩，但不能省略统计核验。

## 15. 目标命令接口

以下是开发完成后的目标接口，不代表现有命令已经支持：

```bash
python -m benchmark.runner \
  --cases benchmark/cases/final_cases.json \
  --arm multi_agent_qa_fixed \
  --source-mode replay \
  --snapshot-id <snapshot-id> \
  --repeat 2 \
  --task-concurrency 2 \
  --out benchmark/results/<run-id>

python -m benchmark.runner \
  --cases benchmark/cases/final_cases.json \
  --arm single_llm \
  --source-mode replay \
  --snapshot-id <snapshot-id> \
  --repeat 2

python -m benchmark.summary \
  --runs <single-run> <no-qa-run> <fixed-qa-run> \
  --content-review <signed-review.json> \
  --out benchmark/results/<summary-id>
```

所有长任务运行前必须用大白话说明：在跑哪一组、预计多少次任务、为什么跑、预计成本和如何停止。

## 16. 最终简历数字输出模板

只有总报告验收完成后，才能把占位符替换为真实值：

> 构建覆盖 **6 个产品、12 个 case、72 次核心任务执行**的可复现 Benchmark，基于固定网页快照、人工黄金标签和失败计 0 口径，评估结构质量、内容可靠性、返工效果与运行成本。完成 **[N] 组配对对照**；多 Agent 相比单次 LLM 的 Gold 覆盖率变化 **[A] 个百分点**，修复后 QA 的实际返工执行率由 **[B]%** 提升至 **[C]%**，字段问题解决率达到 **[D]%**，完整支持率变化 **[E] 个百分点**，Token 成本变化 **[F]%**。

填写规则：

- 若没有提升，写实际下降或“未改善”，不能把占位符默认填成正数。
- 如果人工核验只有 24 个 Slot，面试中必须能说明样本范围。
- 不把引用覆盖率写成准确率。
- 不把 repeat 数写成产品数。
- 不写“统计显著”。
- 简历只保留 2–4 个最有解释力的数字，其余留在总报告。

## 17. 完成定义

只有同时满足以下条件，才称为“完整 Benchmark 已实现”：

- 固定快照回放、单次 LLM 基线、三种核心实验臂和总报告均已实现并测试。
- 主实验、返工对照、内容人工裁决和实时冒烟均有可追溯产物。
- 所有失败与缺失均按预定口径处理。
- 简历中的每个数字都能由总报告追溯到公式、原始结果和签核记录。
- 最终结果无论正向还是负向，都按真实结果报告。
