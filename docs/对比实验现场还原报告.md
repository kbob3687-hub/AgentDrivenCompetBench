# 对比实验现场还原报告

生成时间：2026-11-03。本报告全部数字来自 `benchmark/results/` 磁盘数据（38 个目录，gitignore 保留、未删除），不引用对话记忆。三个方向由子代理分头取证，关键数字我另用脚本独立复核过一遍，复核中发现的**我自己此前写错的记录**也如实列在第 4 节。

---

## 一句话结论

到目前为止真正跑出来的对比实验有两组：

1. **QA 开 vs QA 关（20 对 20，同码同配置）**——结论是"当时的 QA 环节在空转"：11 个任务被判打回重做，实际只完整重做了 **1 次**；代价却是延迟 **1.55 倍**、token **1.14 倍**；各项自动结构指标两组**打平**。这个缺陷后来被代码修掉了，但**修复后的效果还没有数据**。
2. **多 Agent 流水线 vs 单次 LLM（同一冻结快照包，ClickUp，n=1）**——多 Agent 用 **8 倍 token、4.2 倍时间**换到 **2 倍的可溯源证据条数**（86 vs 43），结构指标两组全过。只有 1 个样本，只能说趋势，不能写进简历当成果。

两组实验共同的副产品是：**自动指标测不出内容真假**，所以现在才要做 24 个人工签核的 Gold Slot。

| Git commit | `c6f952eb…`，dirty=true | `c6f952eb…`，dirty=true |

公平性我额外做了一项没在对话里做过的核验：把两个 manifest 的 `source_sha256`（69 个源码文件哈希）逐个比对，**差异文件数 = 0**。也就是说 A/B 两侧跑的代码逐字节相同，这是整个项目里可比性最硬的一组数据。dirty=true 的含义要说清：只能证明"同一份未入库代码"，不能对外宣称是某个提交的效果。

### 2.2 中间两次对照作废（数据全部保留）

**第一次 `20261029T115308Z-9f9ee79f`（11-29 当天）：中转余额打穿。**
前 3 个任务正常（notion-core-001 的 r1/r2/r3，claims 分别 99/85/86），其余 **17 个任务 claims=0**，顶层 `error='no claims available for analysis'`，`collect_errors` 里是 17 个文件各 10 处的原文：

```
https://clickup.com/pricing: APIStatusError: Error code: 402 -
{'message': 'Insufficient Balance…', 'type': 'insufficient_balance_error'}
```

当天 08:53 的试点 run（`20261029T085300Z-238251bb`）里已经出现过同样的 402，说明余额问题当时已有征兆。
如果拿这组直接对比，会得到"QA 开组成功率高 75 个百分点"的**假结论**——那是对手饿死了，不是 QA 厉害。

**第二次 `20261101T112646Z-ec4507a7`（11-01 上午）：网络/代理采集崩了。**
100 次 URL 抓取 **68 次失败**（成功仅 firecrawl 29 / playwright 2 / direct_http 1），错误原文分类：66 条"所有抓取方法均失败 … ConnectError / net::ERR_CONNECTION_CLOSED / Connection aborted"，2 条 direct HTTP 403 + Firecrawl 限流。只有 4 个任务走到 ended，结构指标掉到 0.2。目录里的 `compare.md` 给出的数字（延迟 B−A +12.38s、token B−A −86,806.59、coverage/schema/workflow −0.70）**只是故障表现**，不能当实验结果。

**第三次 `20261101T121038Z-ca0c76a4`（11-01 中午）：有效。**
100 次抓取 **99 成功**（firecrawl 92 / playwright 5 / direct_http 2），仅 1 次失败（g2.com 的 Notion 评价页 403 + 限流）；全 run 无 402、无 0-claims 任务（最少一个任务也有 68 条 claims）；20 任务里 19 ended、1 failed（`clickup-core-001-r4-c1`，`failed to parse LLM analysis output`，与 A 臂那 2 个失败同因）。

### 2.3 结果：QA 当时是个只会挑毛病、不会指挥干活的检查员

A 臂 20 个任务逐文件统计（我直接遍历 `raw/*.json` 复核）：

- 最终状态：completed **7** / source_limited **10** / rejected(score=0.54) **1** / failed **2**
- 首轮 QA 判定：pass **7** / revise **10** / reject **1** / 未走到 QA **2**
- 拦停原因字段 `rework_blocked_reason`：`discovery_found_no_new_urls` **10**、`not_blocked` **1**
- **实际返工重试次数分布：0 次 = 19 个任务，1 次 = 1 个任务**

把这几行合起来就是那次实验的核心事实：**11 个被判"打回重做"，10 个卡在原地，只有 1 个真的完整重做了一遍。**

那个唯一真重做的是 `notion-vs-clickup-001-r5-c2`：QA 打回后 collector→analyst→writer→qa 全链重跑，第二轮又被同一原因拦停，单任务烧掉 184,427 token。

成本侧（`ab_facts.json`，离线重算，不联网不调模型）：

- 延迟：A 均 **224.0s**（中位 221.4 / p90 261 / max 323）vs B 均 **144.3s**（中位 137.1 / p90 184.9 / max 196.9）≈ **1.55×**
- token：A **2,199,833**（入 1,394,284 / 出 805,549）vs B **1,930,699**（入 1,263,915 / 出 666,784）≈ **1.14×**
- LLM 调用次数：159 vs 138 ≈ **1.15×**
- 注意延迟涨幅远大于 token 涨幅，因为返工那一轮多问的问题是短句。

质量侧（配对口径，同 case 同 repeat 才配）：

| 指标（中文口径） | 可用配对 | A 均值 | B 均值 | 差值 B−A |
|---|---|---|---|---|
| Schema 合法率 | 15 | 0.9333 | 0.9333 | **0** |
| 维度覆盖率 | 15 | 0.9333 | 0.9333 | **0** |
| 流程完成率 | 15 | 0.9333 | 0.9333 | **0** |
| 引用挂载率（形式指标） | 13 | 0.9717 | 0.9869 | +0.0151（B 略高） |

**自动指标不支持"QA 提升质量"，反而显示它只增加了成本。**

### 2.4 QA 到底想修什么，为什么修不了

首轮 QA 均分 0.677（区间 0.54–0.73），共开出 **297 条问题**：按类型 missing_source 116 / inconsistency 82 / low_confidence 26 / schema_violation 25 / factual_error 24；按严重度 minor 131 / major 137 / critical 29；最集中的字段是 **swot（52 次）**。

关键细节：那 10 个 `source_limited` 任务的 `missing_dimensions` **全是空的**——QA 要修的不是"缺某个维度"，而是**已写内容的证据不够**。举一条 critical：

> `notion-core-001-r1-c1`：报告里"AI Meeting Notes"相关主张所挂的 4 条来源，**没有一条 snippet 提到会议**，属零证据支撑；建议回到 `notion.so/pricing` 抓取原文段落。

而当时的路由逻辑是：QA 判 revise → 图先回 Discovery 找"没试过的新 URL" → 预设竞品翻来覆去就那 5 个 URL → 找不到新址 → 直接以 source_limited 结束。**既不重抓已有来源，也不让 Analyst/Writer 基于现有 claims 补证据**，闭环等于没闭。这正是修复的靶子。

### 2.5 代码根因与修复

修复提交：`8b699b6`（2026-11-01 21:56）"fix: make QA rework execute actionable repairs"，把字段级反馈直接路由回 Analyst / Writer，同时保留"证据真的不存在时"的 source_limited 停止；改动 `src/orchestrator/{graph,nodes,routing,state}.py`、Analyst/Writer 的 agent+prompts、`src/api/runner.py`，并新增 443 行 `tests/benchmark/test_rework.py`。

**修复后的配对实验还没有跑过。** 上面 20 对数据全部产生于修复之前，因此既不能用来声称"新机制有效"，也不能声称"无效"。

### 2.6 这组数据算不出什么（写进简历的红线）

`ab_facts.json` 里的 `not_computable` 五条，原文口径：

1. 内容准确率（supported/unsupported）——当时没有人工黄金标签核验，只有结构指标；
2. 修复后返工链路的实际效果——数据早于修复 commit `8b699b6`；
3. 每轮新增证据量——旧 claims 没有轮次标记，切不开；
4. token 换算成金额——只存了 token 数，没存当次单价快照；
5. 统计显著性——n=20 且两侧都是 dirty 状态，只能报描述性差异，不写"显著"。

## 3. 实验二：多 Agent 流水线 vs 单次 LLM（ClickUp，n=1）

### 3.1 输入怎么冻结的

回放包 `benchmark/replay_bundles/clickup-core-001-c1/`：5 个 URL、5 个正文 txt（sha256 命名），`frozen_at=2026-11-02T13:09:39Z`，正文的 `observed_at` 逐条落在 2026-11-01 12:14:03–12:15:01，`source_run=20261101T121038Z-ca0c76a4`（就是实验一的 B 有效臂当时真实抓到的文本）。回放全程不联网，缺页直接报错。

复核时发现一个瑕疵，如实记录：**包里那条 capterra 页面的 title 实际是 404 页，但 `success=true`**。这包是正式集之前的旧包，正式 12 包冻结时这类垃圾页已被剔除。

### 3.2 中间 6 个失败 run + 2 次无效对照（全留，未删）

| 目录 | 失败原因（数据原文） |
|---|---|
| `20261102T131916Z-9ca7812d` | 基线只吃到 1 个来源页：`input_tokens=4662`、unique_source=1 → 归档为 **attempt1** |
| `20261102T132218Z-2d2189fd` | `baseline reply is not valid JSON: Expecting ',' delimiter: … (char 11223)`，`output_tokens` 恰为 16384 → 输出被 max_tokens 截断 |
| `20261102T132507Z-a75d7b8f` | `baseline reply missing 'profile' object`（模型输出平铺，无外层包装） |
| `20261102T132737Z-0ccbbc38` | 同上，`reply_head` 显示 `{"company_name":"ClickUp",…` 平铺 |
| `20261102T133003Z-13666e3a` | `error='"profile"'`、8.6s 就结束、tokens=null → 提示词里的字面 `{"profile":…}` 被 `.format()` 当占位符吞掉，KeyError |
| `20261102T133223Z-236f432d` | outcome=completed 但 `swot=null` → 维度没要求到 SWOT，归档为 **attempt2 的 B 臂** |

两次无效对照的数字长什么样（各自的 compare.json）：

- **attempt1**：B 臂 evidence 21、token 15,209、延迟 52.0s、维度覆盖 0.75，各维度来源数都是 1——**"输入吃亏"直接体现在 token 只有正常值的三分之一**。根因是页面拼装用 60000 字总预算 + 命中即 `break`，第 2 页 10 万字触发后整页丢弃，B 只拿到 1/5 页面。修法是改成每页 12000 字截断、不设总量上限，与 `src/agents/collector/agent.py:337` 的 `_truncate_content(max_chars=12000)` 对齐。
- **attempt2**：B 臂没被要求 SWOT（提示词维度误填了采集 scope `resolved_collect_scope`，里面确实没有 swot），维度覆盖必然 0.75，evidence/persona 等指标配对缺失。**根因是"问的问题不同"，不是能力差异。**

这两次都是**我自己跑错、自己发现、自己作废**的，作废依据写在 `notes.md` 和目录名里，数据没删。公平性是靠这轮自我纠错换来的。

### 3.4 本次复核新发现的记录错误（我自己的错，如实列出）

1. `multiagent_vs_singlellm_clickup/notes.md` 里写"同一 Git commit（**c6f952eb** 工作树）"——**错**。两臂 manifest 的 `git.commit` 实际都是 `8b699b62…`，dirty=true。c6f952eb 是实验一的 commit，我写 notes 时串了。
2. notes.md 的失败 run 清单**漏了 `20261102T133223Z-236f432d`**（它其实是 attempt2 的 B 臂 run）。
3. 严格说两臂代码不是逐字节相同：`manifest.source_sha256` 里 **`benchmark/baselines/single_llm.py` 一个文件哈希不同**（A `f4eee1…` / B `3a304b…`），因为两臂之间我还在修基线。该文件多 Agent 臂根本不执行，所以对照仍然成立，但"代码完全一致"这句要限定成"共享链路一致"。
4. 实验一作废臂（`20261101T112646Z`）的 `compare.md` 里**并没有**"本文件仅供故障诊断、不可用于结论"的字样——那句免责只存在于对话里，没落到盘上。这是个真实缺口：光看目录里的文件，第三方有可能误用这组数字。

## 5. 现在可以对外说什么 / 不能说什么

**能说（有磁盘依据）：**

- 用可复现的配对实验定位到一个真实缺陷：20 对同码任务里，11 次 QA 打回只执行了 1 次真实重做，10 次因"找不到新 URL"被拦停；该实验中 QA 增加 14% token、55% 延迟，结构指标无提升。
- 评测体系本身的方法论：每个数字有精确定义和可复核 run_id；失败任务计 0 不许扔样本；A/B 必须同 commit 且校验源码哈希；内容真假刻意不由大模型自评（`llm_judge_score` 留空，改网页存档 + 人工是/否签核）。
- 坏数据不硬用：两次臂作废（402、网络故障）+ 两次基线无效对照，全部改名归档并写明原因，第三/第四次才下结论。

**不能说：**

- "QA 让报告变好了 X%"——修复后一次都没跑过。
- "多 Agent 比单次 LLM 准确率高 X%"——只有 n=1，且内容未人工核验。
- 任何内容准确率、幻觉率数字——24 个 Gold Slot 还在你手上等裁决。
- "统计显著"——样本量和 dirty 状态都不支持。

**措辞注意：** 对外讲这个项目用 "agentic workflow"，别说"多 Agent 自主系统"——图结构是编译期固定的 5 个节点，只有 QA 环节由模型给 verdict 决定回环，要的是可复现和成本可控，不是自主性。
